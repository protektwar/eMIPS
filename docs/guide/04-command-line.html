Phase 4 — The command line

Guide contents · previous: Phase 3 — The GUI in depth · next: Phase 5 — Understanding what you see

Everything the window does is also available in a terminal: assemble, disassemble, run, show the pipeline, and debug interactively. The terminal runs the same engine as the window, so results are identical. It is handy over SSH, for quick checks, and for scripts — a teacher's worksheet can be a list of debugger commands.

All commands start with python3 -m emips (run from the eMIPS folder, or anywhere once installed with pip). The transcripts below are real output — the test suite re-runs them.

4.1 Overview

Command Does
asm FILE assemble: print the listing, optionally write Intel HEX
dis FILE.hex disassemble the words of an Intel HEX file
run FILE run a program; then print the registers (and more)
pipe FILE run on the 5-stage pipeline: chart, CPI, stalls, events
debug [FILE] the interactive debugger
gui [FILE] open the window
cc FILE.c build a C program into an ELF executable
gdb FILE let GDB debug the program (GDB's remote protocol)
check FILE run the program as its checks say: which pass, which fail

python3 -m emips COMMAND --help lists every option of a command.

4.2 Options shared by several commands

Option Commands Meaning
--release R1|R2|R3|R5|R6 all the MIPS32 / MIPS64 release (default R5; nanoMIPS: R6, the only one)
--arch mips32|mips64|nanomips all the architecture (default mips32): mips64 = a MIPS64 core — 64-bit registers, HI / LO and PC, the doubleword instructions (daddu, ld, dsll32, dmult ...), dli / dla, the n64 register names ($a4–$a7 = $8–$11, $t0–$t3 = $12–$15); with the fixed mapping it addresses the 32-bit compatibility segments (Config.AT = 1: any other 64-bit address is an Address Error), with a TLB (--mmu tlb, ftlb, +sc, +pw) the whole 64-bit address space (Config.AT = 2: xuseg, xsseg, xkphys, xkseg; the boot firmware sets Status.KX / SX / UX and handles the XTLB Refills); it runs in instruction mode and on the 5-stage pipeline (the 24K is a MIPS32 core: --model 24k becomes 5-stage; DMULT / DDIV take the MIPS64 5K's 9 / 67 cycles); the boot sets Status.FR (64-bit FPRs), the user boot Status.PX (64-bit operations in User Mode). nanomips = a nanoMIPS32 core (the I7200's instruction set): 16-, 32- and 48-bit instructions, Release 6 based, no delay slots, no FPU; the program is assembled and linked as the nanoMIPS toolchain's as and ld do (the same bytes); the p32 register names ($t4 / $t5 = $2 / $3, $a0–$a7 = $4–$11, $t0–$t3 = $12–$15) — so the system call number goes in $t4, its arguments in $a0–$a2; every MMU, caches and cores, the Malta (--board malta: its boot monitor as nanoMIPS code); instruction mode and the 5-stage pipeline (--model 24k becomes 5-stage: the 24K is a MIPS32 core); nanoMIPS ELF executables, C (cc --arch nanomips, 4.11) and GDB (nanomips-elf-gdb, 4.12)

--relax all nanoMIPS: the linker's relaxations (ld --relax) of a .linkrelax program — calls, branches and $gp accesses that fit a shorter form once every address is known are shrunk; asm prints what the linker did (# ld: ... lines; the expansions of what does not reach happen without it) (Lab 65)

--cache-parity run, pipe, debug, gdb the caches have parity (ErrCtl.PE, the Cache Error exception)
--cache-init random|hardware run, pipe, debug, gdb cache contents after reset: random (default) or invalid
--l2 / --l3 SIZE[:WAYS[:LINE]] run, pipe, debug, gdb an L2 (256K: 8-way, 32-byte lines; 512K:4:64) and, below it, an L3 (2M)

--nonblocking run, pipe, debug, gdb pipeline: loads miss in the background (hit under miss)
--model 5-stage|24k run, pipe, debug, gdb the pipeline model: the textbook 5-stage pipeline (default) or the MIPS 24K's 8 stages with branch prediction (Phase 5)
--cores N run, pipe, debug, gdb a multi-core system of N cores (2–6; MIPS32 or MIPS64): one memory, the Coherence Manager (coherent data caches, the shared L2), the Cluster Power Controller; the kernel / user boot starts every core at the entry, --boot reset core 0 only (Phase 5, 5.9); run prints the cores at the end, pipe (and run --pipeline) also every other core's cycles and CPI (the chart is core 0's); with --board malta a multi-core Malta (Phase 5, DMA)
--iocu run, pipe, debug, gdb with --board malta --cores N: an I/O Coherence Unit — the PCI DMA is coherent with the data caches (Phase 5, DMA)
--shadow-sets N run, pipe, debug, gdb GPR shadow sets, 1–16 (default 4, a 24K's most; Release 2+): what SRSCtl.HSS says, the sets an exception / vectored interrupt switches to (Phase 5, 5.10)
--compressed auto|none|mips16e|micromips|micromips-only run, pipe, debug, gdb the core's compressed ISA: auto (default) = MIPS16e from Release 1 to 5, as the 24K, none in Release 6; none = a MIPS32 core without one (jalx is Reserved, a jr to an odd address an address error); mips16e (Config1.CA, Phase 2, 2.19); micromips = microMIPS32 and MIPS32, Release 2+ (Config3.ISA = 2; the M14K is a Release 2 core with microMIPS); micromips-only = no MIPS32 (Config3.ISA = 1; 2.20); a program with MIPS16e / microMIPS code gets it anyway (with --arch mips64, auto gives one only then)
--no-fpu run, pipe, debug, gdb a core without an FPU, as the 24Kc: Status.CU1 reads 0, every FPU instruction is Coprocessor Unusable (Config1.FP = 0); a C program is built -msoft-float
--dsp auto|none|dsp|dspr2 run, pipe, debug, gdb the DSP Module (SIMD on bytes and halfwords, saturating fractional arithmetic, the accumulators $ac1–$ac3, DSPControl): auto (default) = Revision 2 when the program has DSP instructions, none otherwise (the 24K has none); none; dsp = Revision 1 (the 24KE, the 1004K); dspr2 = Revision 2 (the interAptiv, the microAptiv; Revision 3 on Release 6); Release 2 or later; Config3.DSPP / DSP2P, Status.MX enables it. With --arch nanomips: the nanoMIPS DSP ASE (the same instructions in nanoMIPS encodings, Revision 3)
--mt auto|none|VPES:TCS run, pipe, debug, gdb the MT Module (thread contexts and VPEs: Phase 2, 2.22): auto (default) = 2 VPEs and 5 TCs, as a 34K, when the program has MT instructions, none otherwise; none; VPES:TCS = 1–2 VPEs, up to 9 TCs; Releases 2–5; with --cores every core has them (the 1004K, the interAptiv); pipeline mode runs the 34K's pipeline. With --arch nanomips: the nanoMIPS MT ASE (the same thread contexts and VPEs, nanoMIPS encodings), in instruction mode
--mt-pm rr|wrr|wrr2 run, pipe, debug, gdb the MT Module's policy manager, which TC issues: rr (default) round-robin, wrr weighted round-robin (TCSchedule.GRP groups, VPESchedule.GPO), wrr2 with throttles on the core's queues (Phase 5)
--itc auto|none|FIFOS:SEMS run, pipe, debug, gdb the MT Module's ITC gating storage: auto (default) = 4 FIFO + 8 semaphore cells; none; FIFO and semaphore cells 0, 1, 2, 4, 8 or 16 each
--vps N run, pipe, debug, gdb Release 6 virtual processors a core (1–4; the I6400's 1, 2 or 4): more than one makes the I6400's CM3 system, even of one core — DVP / EVP, the CPC starts and stops the VPs, VP numbers core × 4 + VP (Phase 5); Release 6 only
--itu auto|none|FIFOS:SINGLES[:DEPTH] run, pipe, debug, gdb a CM3 core's ITU (the I6400's gating storage, placed by CP0 SAAR): auto (default) = 4 FIFO cells of 4 entries + 8 single-entry cells; none; up to 32 cells, FIFOs of 2, 4 or 8 entries
--core NAME run, pipe, debug, gdb a real MIPS core (24kf, m14k, p5600 ...; 4.13): its release, compressed ISA, FPU, MMU, caches, cores, shadow sets, pipeline model and PRId; the other flags choose among what the core can be built with, a flag it cannot have is refused (Phase 6, 6.11)
--no-header asm, run, pipe, debug, gdb ignore the program's # eMIPS: line (without it, that line supplies the flags you do not give: What's in eMIPS); a combination of flags that does not go together is refused with the reason
--board SPEC asm, run, pipe, debug the board: flat (default: every physical address is RAM, the MARS layout) or malta[:RAM_MB[:SWITCHES[:MHZ]]] — the MIPS Malta (MHZ: the core's clock, default 10): the GT-64120's memory map, bus errors, the LEDs / display / switches, programs in kseg0 (Phase 5, A real board)
--disk [SLOT=]IMAGE run, pipe, debug an IDE disk on the Malta (with --board malta; repeatable): SLOT pri0 (the default, then pri1, sec0, sec1), IMAGE a file (its bytes are the sectors) or blank:SIZE (blank:8M); every run starts from the image (Phase 5, An IDE disk)
--mmu SPEC run, pipe, debug the MMU: fixed (default), bat, tlb[:N] (a 24K's TLB, N = 32), ftlb[:N[:SETSxWAYS]] (VTLB + FTLB, 64 + 128x4); a TLB takes +sc (segmentation control, EVA) and +pw (page table walker), e.g. ftlb+sc+pw; on a MIPS64 core (--arch mips64) fixed and bat keep 32-bit addresses, a TLB gives the 64-bit address space — with +sc the xkphys regions of SegCtl1.XAM / SegCtl2.XR and a 64-bit EBase, with +pw 64-bit page tables (PWSize.PS, PWCtl.XK / XS / XU) (Phase 5); on a nanoMIPS core also mpu[:N] (the I7200's memory protection unit with N regions, 16 by default: PA = VA, segments and regions with RI / WI / XI) and fixed+mpu[:N] (the fixed mapping with N MPU regions) (Phase 5, The other MMUs)

They mean the same as the window's Settings (Phase 3, 3.11).

4.3 asm — assemble

$ python3 -m emips asm emips/gui/examples/sum_array.asm
00400000  3c081001  lui $t0, 0x1001                  # main:   la    $t0, nums
00400004  25080000  addiu $t0, $t0, 0                # main:   la    $t0, nums
00400008  24090004  addiu $t1, $zero, 4              # li    $t1, 4
0040000c  00005025  or $t2, $zero, $zero             # move  $t2, $zero
00400010  8d0b0000  lw $t3, 0($t0)                   # loop:   lw    $t3, 0($t0)
...

Each line: address, machine word, the instruction as the processor sees it, and the source line it came from — so you see what every pseudo-instruction became. An error stops with the line number: prog.asm: line 2: unknown instruction 'lii'.

--hex FILE.hex also writes the program as Intel HEX.

4.4 dis — disassemble Intel HEX

$ python3 -m emips asm emips/gui/examples/sum_array.asm --hex sum.hex
...
$ python3 -m emips dis sum.hex
00400000  3c081001  lui $t0, 0x1001
00400004  25080000  addiu $t0, $t0, 0
00400008  24090004  addiu $t1, $zero, 4
...

(asm --hex prints the listing too.) dis decodes every complete word in the file (data too — it cannot tell code from data). Use the same --release and --little the code was made for.

4.5 run — run a program

run runs until the program exits, runs past its last instruction, reaches a breakpoint, or --steps (default 100 000; on the Malta 1 000 000, its serial output is slow) are done. Its output appears as it is printed; when it reads input (read_int ...), type the input in the terminal (or pipe it in: echo 7 | python3 -m emips run prog.asm). Then the registers:

$ python3 -m emips run emips/gui/examples/sum_array.asm
sum = 18

--- 37 steps, pc = 0x0040004c, 37 cycles (exited)
$zero 0x00000000    $at 0x00000000    $v0 0x0000000a    $v1 0x00000000
  $a0 0x00000012    $a1 0x00000000    $a2 0x00000000    $a3 0x00000000
  $t0 0x10010010    $t1 0x00000000    $t2 0x00000012    $t3 0x00000006
...
   pc  0x0040004c    hi  0x00000000    lo  0x00000000
Option Meaning
--steps N stop after N steps
--break LOC stop before the instruction at LOC (repeatable)
--until LOC stop when LOC is the next instruction
--trace print what happens inside every instruction
--cp0 also print the CP0 registers
--fpu also print the FPU registers
--mem LOC[:WORDS] also print memory from LOC (repeatable)
--cache-stats also print the cache statistics: hits, misses, the 3 C's (Phase 5)
--tlb-stats also print the TLB statistics: lookups, hits, misses, exceptions, page walks (Phase 5)
--perf EVENT[,EVENT] set the performance counters to count these events (user and kernel mode) and print them at the end (Phase 5)
--pipeline run on the 5-stage pipeline and print the chart (as pipe)

A location (LOC) is an address (0x00400010), a source line number (12), a label (loop), or a register holding an address ($sp).

$ python3 -m emips run emips/gui/examples/factorial.asm --break fact --mem '$sp:4'
stopped at 0x00400020  addiu $sp, $sp, -8               line 13: fact:   addiu $sp, $sp, -8      # push $ra and $s0

--- 3 steps, pc = 0x00400020, 3 cycles
...
--- memory $sp
0x7fffeff0  00000000 00000000 00000000 00000000  ................

(The quotes around '$sp:4' stop the shell from replacing $sp.)

--trace prints, for every instruction, its fields, what the ALU did and where its operands came from, the memory access and the registers it changed:

$ python3 -m emips run emips/gui/examples/sum_array.asm --trace --steps 2
0x00400000: lui $t0, 0x1001   (I-format, 0x3c081001)
  decode: op[31:26]=001111 LUI | rs[25:21]=00000 $zero | rt[20:16]=01000 $t0 | immediate[15:0]=0001000000000001 4097
  ALU: b << 16; b = 0x00001001 from immediate 0x1001 (zero-extended) -> 0x10010000
  $t0: 0x00000000 -> 0x10010000
0x00400004: addiu $t0, $t0, 0   (I-format, 0x25080000)
  decode: op[31:26]=001001 ADDIU | rs[25:21]=01000 $t0 | rt[20:16]=01000 $t0 | immediate[15:0]=0000000000000000 0
  ALU: a + b; a = 0x10010000 from $t0 (register file); b = 0x00000000 from immediate 0x0000 (sign-extended) -> 0x10010000
...

The memory-mapped keyboard gets its keys from --keys (the newline is a key too):

$ python3 -m emips run emips/gui/examples/mmio_echo.asm --keys "ok\n"
...

(\n is typed literally here; in a shell, --keys $'ok\n' passes a real newline. Both work.)

4.6 pipe — the 5-stage pipeline

pipe runs the program on the 5-stage pipeline and prints the pipeline chart (one row per instruction, one column per cycle; -- is a stall in ID), the cycle count, the CPI and the stall cycles by cause. --events adds what happened each cycle:

$ python3 -m emips pipe emips/gui/examples/pipeline_hazards.asm --events --width 24
...
00400008   lw $t1, 0($t0)                     IF ID EX ME WB
0040000c   addu $t2, $t1, $t1                    IF -- ID EX ME WB
...
0040002c   mul $s0, $t7, $t7                                                   IF ID EX EX EX EX ME WB
00400030   addu $s1, $s0, $s0                                                     IF -- -- -- ID EX ME WB
...
24 cycles, 15 instructions retired, CPI 1.60
stall cycles: branch 1, ex-busy 3, load-use 1
    4  forward $t0: EX/MEM -> EX (lui $t0, 0x1001 -> addiu $t0, $t0, 0)
    5  load-use: $t1 from lw $t1, 0($t0)
...
   13  forward $t7: EX/MEM -> ID (or $t7, $t6, $t5 -> beq $t7, $zero, 0x00400034)
   13  beq $t7, $zero, 0x00400034: not taken
...
Option Meaning
--cycles N stop after N cycles (default 10 000)
--width N how many cycles the chart shows (default 40)
--events forwarding, stalls, branch decisions, flushes per cycle (every cycle of the run: without it eMIPS keeps the first 1000 and the last 4000)
--views the events plus the full view of the instructions in ID and EX
--cache-stats the cache statistics at the end (as run)
--tlb-stats the TLB statistics at the end (as run)
--perf EVENT[,EVENT] the performance counters (as run)
--no-forwarding without forwarding paths — compare the CPI 
$ python3 -m emips run emips/gui/examples/pipeline_hazards.asm --pipeline --no-forwarding
...
37 cycles, 15 instructions retired, CPI 2.47
stall cycles: ex-busy 3, no-forwarding 15

Rows marked (no code here) at the end are instructions the pipeline had already started fetching after the program's last instruction; they never execute.

4.7 debug — the interactive debugger

$ python3 -m emips debug emips/gui/examples/factorial.asm
eMIPS debugger — MIPS32 R5, big-endian, instruction mode. Type help.
=> 0x00400000  addiu $a0, $zero, 5              line 4: main:   li    $a0, 5
(emips) break fact
breakpoint at 0x00400020  addiu $sp, $sp, -8               line 13: fact:   addiu $sp, $sp, -8      # push $ra and $s0
(emips) continue
breakpoint
   0x00400008  nop
=> 0x00400020  addiu $sp, $sp, -8               line 13: fact:   addiu $sp, $sp, -8      # push $ra and $s0
(emips) continue
breakpoint
   0x00400044  nop
=> 0x00400020  addiu $sp, $sp, -8               line 13: fact:   addiu $sp, $sp, -8      # push $ra and $s0
(emips) regs $a0 $ra
   $a0 = 0x00000004  4
   $ra = 0x00400048  4194376
(emips) delete fact
(emips) finish
   0x0040005c  nop
=> 0x00400048  mul $v0, $v0, $s0                line 21: mul   $v0, $v0, $s0
(emips) regs $v0
   $v0 = 0x00000018  24
(emips) quit

How to read it:

  • => is the next instruction (not executed yet), with its source line. In pipeline mode it is the instruction about to enter EX.
  • The indented line before it is the instruction just executed and what it changed (; $t3 = 0x00000003, ; [0x7fffeff8] = 0x0040000c). Here it is the nop in a delay slot (the jump's, or the jal's).
  • The second continue stopped in the recursive call fact(4) ($a0 = 4); finish ran until that call returned to fact(5) — $v0 = fact(4) = 24.

Start it without a file and use load FILE at the prompt. Press Ctrl+C to stop a long run (the debugger stays), Ctrl+D or quit to leave. When the program reads input, the debugger asks for it (program input>) — or give it beforehand with input TEXT.

4.8 Debugger commands

help lists them; help COMMAND explains one. Short forms are in brackets.

Running

Command Does
step [N] (s) N instructions — or N clock cycles in pipeline mode
next [N] (n) like step, but a call (jal, jalr, bal, balc ...) runs to its return as one step
back [N] undo N steps
continue [N] (c, run, r) run until a breakpoint, the end, an error or an input request (at most N steps)
stepline [N] (sl) run to the next source line — a C line of a compiled program, a source line of an assembly one; into calls
nextline [N] (nl) like stepline, but a call runs as one step
until LOC (u) run until the instruction at LOC is next
finish run until the current function returns to its caller (by the call stack: a recursive call returning to the same address does not stop it)
reset restart the program (breakpoints and given input are kept)

Breakpoints: break LOC (b) sets one, break alone lists them, delete LOC (d) or delete all removes them. For a compiled program (an ELF with line information) LOC can be a C line — 17 (the current file; main's before the program gets there) or file.c:17 — or a function name; a line that starts in several places (a for with its condition and increment) gets a breakpoint on each.

Looking

Command Shows
regs all 32 registers, PC, HI, LO (* = changed by the last command)

cp0 PC, HI, LO, Status, Cause, EPC, BadVAddr, Count, Compare, IntCtl, SRSCtl, SRSMap (in Debug Mode Debug, DEPC, DESAVE), FCSR

4.11 cc — build a C program

python3 -m emips cc prog.c [more.c lib.S] [-o prog.elf] [--release R1|R2|R3|R5|R6]
                    [--arch mips32|mips64|nanomips] [--nms] [--little] [-O 0|1|2|3|s]
                    [--mips16 | --micromips] [--no-fpu] [--dsp | --dspr2] [--core NAME] [-v]

Builds an ELF executable for eMIPS with clang or a MIPS GCC (and GNU ld or ld.lld): crt0, libemips.c and the sources, linked for the eMIPS memory map (Phase 2, 2.18). --mips16 compiles the C as MIPS16e (16-bit instructions, 2.19; it needs a MIPS GCC), --micromips as microMIPS (2.20; Release 2, 3 or 5, the default with it is R5). In both, crt0 stays MIPS32 and the linker turns the calls between the two ISAs into jalx. --arch mips64 builds for MIPS64, the n64 ABI: an ELF64 (64-bit long and pointers; GNU ld's elf64btsmip / elf64ltsmip). --arch nanomips builds for nanoMIPS, the p32 ABI, with MediaTek's nanomips-elf-gcc on PATH (release nanoMIPS-2022.03-01, GCC 11.2: the later releases ship no compiler) and its linker: soft float (nanoMIPS has no FPU), the nanoMIPS assembler's memory map (code at 0x00400000; at 0x10010000 the data, then _gp and the small data the compiler reaches from $gp), the result of main in $a0; --nms builds for a core of the nanoMIPS subset (-march=32r6s; a full-ISA ELF is refused on one). That release has libgcc — the soft-float arithmetic, 64-bit division — for little-endian full-ISA code only: other builds work while they need none of it, and say so when they do. --no-fpu builds for a core without an FPU (-msoft-float): integer code needs nothing more, float arithmetic calls the soft-float routines (__addsf3 ...) of a MIPS GCC's soft-float libgcc — a toolchain without one (Debian's mips-linux-gnu) is refused with the reason. --dsp / --dspr2 let the C use the DSP Module, Revision 1 / 2 (-mdsp / -mdspr2: GCC's __builtin_mips_addu_s_qb ... on the vector types v4i8 / v2q15; Release 2, 3 or 5); the ELF says so in its ABI flags, and the core that runs it gets the DSP Module. A C program in the window or given to run is built with -mdspr2 when it calls these builtins. With --arch nanomips, --dsp is the nanoMIPS DSP ASE (nanomips-elf-gcc -mdsp, the same builtins). --core NAME builds for that core's release and DSP Module, soft-float when it has no FPU. -v prints the commands it ran. run, pipe and debug take a .c file too (built for the session's release, byte order and architecture) and every command takes the .elf: dis prog.elf prints its listing — the disassembly with each C line above its instructions.

4.12 gdb — debugging with GDB

python3 -m emips gdb FILE [--port N] [--host ADDRESS] [--pipeline] [the run options]

Loads the program (assembly, C, ELF or Intel HEX) and waits for GDB, the GNU debugger, on a TCP port (1234; --port 0 takes any free one). eMIPS then plays the part a JTAG probe or QEMU's -s plays for a real MIPS: GDB's remote serial protocol. GDB reads and writes the registers and memory, sets breakpoints, steps, continues and stops the program with Ctrl-C. The program's output goes to GDB, and its exit ends the session. You need a GDB that knows MIPS: gdb-multiarch (Debian / Ubuntu package gdb-multiarch) or a mips-linux-gnu-gdb.

What GDB sees:

  • The registers of GDB's MIPS target description: the 32 general registers, status, lo, hi, badvaddr, cause, pc, the FPU's f0–f31, fcsr and fir. The FPRs are 64 bits wide when Status.FR = 1, as in Release 6. Writing $pc moves the program, like the debugger's set pc. The architecture follows the release (mips:isa32, mips:isa32r2, mips:isa32r6), and so does the byte order (--little).
  • Memory through virtual addresses, as the program sees it: the caches' dirty data, the TLB's mapping. An address that nothing maps (or, on the Malta, a bus error) is an error in GDB, never an exception in the program.
  • Breakpoints are kept by eMIPS (no break instruction is written into the code), so a breakpoint in a branch delay slot works. Stepping: GDB steps MIPS code itself, with a temporary breakpoint on each address the instruction can go to. A stepi on a branch therefore runs its delay slot too, as on a real MIPS board.
  • Exceptions taken through CP0 run the handler as usual. With --exceptions stop the program stops on the faulting instruction, and GDB gets the signal a MIPS Linux kernel would send: SIGSEGV (address errors, TLB faults, no code at the PC), SIGBUS (bus errors), SIGILL (a reserved instruction, coprocessor unusable), SIGFPE (integer overflow, an enabled FPU exception), SIGTRAP (break, the trap instructions, and running past the program's last instruction). Ctrl-C stops the program with SIGINT.
  • Leaving: detach or quitting GDB ends emips gdb; kill too. A program that reads the console gets its input from the terminal emips gdb runs in.

Watchpoints in GDB

watch, rwatch and awatch stop the program when it writes, reads or touches an address: GDB's hardware watchpoints, kept by eMIPS like the breakpoints. Every load and store checks them, the program's own (the kernel's too) but not GDB's reads, a view or the disk's DMA. As a MIPS watch exception does, the stop comes before the access. GDB then executes that one instruction and shows the old and the new value; a store of the value already there does not stop. The symbols of an assembly program have no type, so give the size with a cast — watch *(int *)&count, or an address:

(gdb) watch *(int *)0x10010008
Hardware watchpoint 1: *(int *)0x10010008
(gdb) continue
[Switching to Thread 3]

Thread 3 hit Hardware watchpoint 1: *(int *)0x10010008

Old value = 0
New value = 1575
sum () at cores_sum.asm:21
21              li    $t5, 1

Threads are cores

With --cores N each core is a GDB thread: info threads lists them with their state, thread 3 shows core 2's registers and frame, and a stop names the core that stopped — the watchpoint above caught core 2 storing its part of cores_sum.asm. The cores run together, as they do in eMIPS (GDB's all-stop mode): a continue or a step moves every running core, and a stop stops them all. With the MT Module the threads are the thread contexts (on a multi-core 1004K or interAptiv, every core's TCs in turn): info threads names each one's VPE and state ("TC 1 on VPE 0, running"), thread N shows its registers, and a free or halted TC is a thread that does not move.

monitor: the eMIPS debugger's commands

monitor CMD runs a command of eMIPS's own debugger (4.8) on GDB's current thread and prints what it says: what GDB cannot show — monitor cache stats, monitor tlb, monitor cps, monitor chart (the pipeline), monitor translate $sp, monitor board ... (gdb) monitor translate $sp
0x7fffeffc kuseg -> physical 0xbfffeffc  (fixed mapping: PA = VA + 0x40000000 (Config.KU); attribute 5 = cacheable coherent, write-back (CPS))

GDB in pipeline mode

--pipeline (and --model 24k) runs the program on a pipeline while GDB debugs it: the cycles, the caches' timing and Count are the pipeline's. GDB still sees the program one instruction at a time. A stop is always at a precise point: every older instruction has executed, the one at $pc has not. In the 5-stage pipeline a branch is decided in ID while the instruction before it executes in EX, so no clock edge lies between the two. A breakpoint on a branch therefore keeps it from executing in ID: it reaches EX unexecuted, the program stops there, and when it goes on the branch is fetched again. That costs a few cycles at each stop, as a debug exception does; monitor chart shows it. A watchpoint holds its load or store for one cycle. Writing $pc flushes the pipeline.

GDB in MIPS16e and microMIPS code

In 16-bit code the stub gives $pc with bit 0 set, as a real target does: that bit is how GDB knows which ISA to disassemble and to step. The ELF the stub hands an assembly program to GDB marks the labels of MIPS16e / microMIPS code (STO_MIPS16 / STO_MICROMIPS) and says which ISA the program uses in its header, as GNU ld does, so break, x/i $pc, stepi, next and bt work in both. A breakpoint there is at the odd address (Breakpoint 1 at 0x400083); writing an odd $pc switches the core to the 16-bit ISA.

GDB and the window

Run → GDB Server does the same for the program in the editor (port 1234; the key gdb_port of the settings file changes it). While GDB is connected it runs the program, and the window's run controls wait. The views follow: GDB's breakpoints are marked in the editor's margin, each stop shows the registers, the datapath and the pipeline, and a program's input comes from the Console pane. When GDB leaves, the window has the program again; a GDB that connects after the program has ended starts it again.

Labs 38–40 (Phase 5) use GDB: a C bug found with a watchpoint, a race between two cores watched access by access, and what a watchpoint cannot see (DMA).

On a core without an FPU (--no-fpu, the 24Kc) GDB still has its FPU registers (its MIPS description needs them) but shows them as <unavailable>. With the DSP Module GDB also has $hi1, $lo1 ... $hi3, $lo3 and $dspctl (its org.gnu.gdb.mips.dsp registers, 72-78).

A MIPS64 program (--arch mips64, or an ELF64 from cc --arch mips64) gets GDB's 64-bit description: every register 64 bits wide, the architecture mips:isa64 / mips:isa64r2 / mips:isa64r6. The ELF eMIPS writes for an assembly program is an ELF64 then, so GDB uses the n64 ABI (show mips abi). Its addresses are 64-bit: a kseg0 one reads 0xffffffff80001000, and with a TLB the whole 64-bit space works — x/1gx, watch on a long, set var $t0 = 0x1111222233334444. With Status.FR = 0 each FPR shows its 32-bit word.

A nanoMIPS program (--arch nanomips, or an ELF from cc --arch nanomips) is debugged with the nanoMIPS toolchain's nanomips-elf-gdb: the stub gives it nanoMIPS GDB's description — r0–r31 (shown with their p32 names), pc, status, badvaddr, cause; no hi / lo and no FPU registers, which a nanoMIPS core does not have. The ELF eMIPS writes for an assembly program is a nanoMIPS one (EM_NANOMIPS, the p32 ABI), with a line table for the 16-, 32- and 48-bit instructions.

4.14 check — does the program do what it should?

python3 -m emips check FILE [--checks CHECKS] [--limit N] [--quiet] [shared options]

An exercise says what a finished program must do: print the right thing, leave a value in a register or in memory, take no more than so many cycles. Written down as checks, check runs the program and says which hold (in the window: Run → Check, Phase 3). A check is a line — a comment in the program, so a student checks their own work:

# check: output is "36"          (it computes the same sum)
# check: stalls == 0             (nothing waits)
# check: cycles <= 53

or the same lines (the # may go) in a file of their own, which a teacher keeps — --checks FILE then replaces the program's own. A program without check: lines uses the checks file named like it, next to it: Lab 3's (Phase 5) is docs/guide/labs/lab3_sum.check, and the program as handed out fails two of them:

$ python3 -m emips check docs/guide/labs/lab3_sum.asm
36
--- 77 cycles, 57 instructions retired, 16 stall cycles
PASS  the program finishes
PASS  output is "36" (it computes the same sum)
FAIL  stalls == 0 (nothing waits): 16
FAIL  cycles <= 53 (and the delay slot does useful work): 77
--- 2 of 4 checks passed

and a solution passes them all:

$ python3 -m emips check docs/guide/labs/lab3_solution.asm --checks docs/guide/labs/lab3_sum.check --quiet
--- 53 cycles, 49 instructions retired
PASS  the program finishes
PASS  output is "36" (it computes the same sum)
PASS  stalls == 0 (nothing waits)
PASS  cycles <= 53 (and the delay slot does useful work)
--- all 4 checks passed

A failed check shows what the run had. A text in parentheses at the end of a check is a note, printed with it. Every run also checks that the program finishes — exits, or runs past its last instruction — without an error, within the step limit. The exit status is 0 when every check passes, 1 when one fails, 2 when the checks (or the program) cannot be read: a script can check a folder of programs, for f in *.asm; do python3 -m emips check "$f" --checks lab3_sum.check --quiet || echo "$f"; done.

What a check can test:

Check Passes when
output is "TEXT" the program's console output is TEXT (white space at the end not compared); \n is a new line; output == "TEXT" / != as is / is not
output contains "TEXT" TEXT is somewhere in the output
output matches "REGEX" the Python regular expression is found in the output, e.g. "bad address 0x[0-9a-f]{8}"
$t2 == 36, $8 != 0, hi, lo, pc a register after the run, compared with a number (-5, 0x24), a character ('A') or a label (its address, nums+32)
word[nums+4] == 2, half[LOC], byte[LOC] memory at LOC — a label, a number or $reg, + / - an offset — in the program's byte order
$f2 == 0x3e99999a, $f2.s == 0.3, $f4.d == 2.5, float[LOC], double[LOC] an FPU register's bits, or the single / double it (or memory) holds — the number is rounded to that format first
cycles <= 53 clock cycles (pipeline mode; in instruction mode the machine's cycles)
instructions, steps instructions retired (instruction mode: executed); the run's steps
stalls == 0, stalls load-use == 0 stall cycles, all or of one kind (pipeline mode; the kinds pipe lists)
exceptions == 0 exceptions taken
exit code == 3 the code of syscall 17 (0 after syscall 10)
cpu 1 $t0 == 1 any check on core (or VPE) 1 of a multi-core system

== and != compare the bits ($t0 == -1 is $t0 == 0xffffffff); <, <=, >, >= the signed values. The machine is the program's # eMIPS: line (What's in eMIPS) and the options given; lines before the checks set up the run:

Line Does
eMIPS: FLAGS the machine for this run (checks files only: in a program the eMIPS: line is the program's own)
input: LINE one line for a read syscall (one line per read)
keys: TEXT keystrokes for the MMIO keyboard (\n = Enter)
limit: N the most steps the run may take (default 100 000, on the Malta 1 000 000; also --limit N)
after: N check after N steps — the program need not have finished (it may loop for ever)
run: NAME a new run, with settings and checks of its own

Several runs test a program with several inputs or on several machines; settings after a run's checks begin the next run:

input: 5
check: output is "120"
run: zero
input: 0
check: output is "1"
run: the 24K
eMIPS: --pipeline --model 24k
input: 5
check: cycles < 400

Writing checks for an exercise

For a teacher, the way that works:

  1. Solve the exercise first, then write the checks and run them on your solution until they all pass — and on the program as you hand it out: it should fail exactly the checks the exercise is about. The labs of this guide that have checks (5.12) were made so: docs/guide/labs/*.check are examples.
  2. Check what a correct program does, not how: its output, the values it leaves where the exercise says they go (a result in $v0 by the calling convention, an array in memory). A register a student may choose freely is not a good check.
  3. Budgets — cycles, stalls, instructions — suit performance exercises. Measure your solution; leave room when other good solutions take a few more cycles.
  4. Several runs try several inputs, the edge cases included (0, a negative number, the largest one); limit: keeps a program that loops for ever from holding up the rest, after: checks one that never ends by design (an interrupt-driven loop).
  5. Notes — (the square of a negative is positive) — are printed with the result: they are the hint a student gets for a failed check.

Keep the checks file yourself, and hand out the program (with checks of its own, or none): --checks replaces what the program says. The example Console input / output (File → Examples) squares the number it reads; three runs check it:

run: seven
input: 7
check: output contains "squared = 49"
run: a negative number
input: -3
check: output contains "squared = 9"   (the square of a negative is positive)
run: zero
input: 0
check: output matches "^Enter a number: "    (it asks first)
check: output contains "squared = 0"

$ python3 -m emips check emips/gui/examples/hello_input.asm --checks docs/guide/labs/squared.check --quiet
--- run 1: seven
--- 19 steps, 19 cycles
PASS  the program finishes
PASS  output contains "squared = 49"
--- run 2: a negative number
--- 19 steps, 19 cycles
PASS  the program finishes
PASS  output contains "squared = 9" (the square of a negative is positive)
--- run 3: zero
--- 19 steps, 19 cycles
PASS  the program finishes
PASS  output matches "^Enter a number: " (it asks first)
PASS  output contains "squared = 0"
--- all 7 checks passed

Checking a folder of submissions is a loop over the exit status — here the names of the programs that fail, and every report in a file:

for f in submissions/*.asm; do
    python3 -m emips check "$f" --checks squared.check --quiet > "$f.txt" || echo "$f"
done
